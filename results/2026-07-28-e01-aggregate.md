# E01 definitive paired-draw baseline

## Executive verdict

E01 completed the untouched 5-suite matrix: 59 cases, 236 claims, three
conditions, and three paired draws, for 531 definitive case-runs.

- **Parity gate: not met.** For the fair comparison, `service_api` minus
  `filesystem_sidecar` was -4.667 claims per 236-claim corpus draw, with a
  case-clustered bootstrap 95% CI of [-13.667, 4.333]. Non-inferiority is not
  declared because the lower bound, -13.667, is not above the predeclared
  -5-claim margin. This failure to establish non-inferiority is not proof that
  the service is inferior.
- **Paired RuptureOps overfetch: absent.** `service_api` produced 63,090
  model-visible tool-output characters per case versus 142,640 for
  `filesystem`, a paired difference of -79,549 with 95% CI
  [-111,508, -49,126]. The service did not exceed files by the required
  15,000 characters; it was lower in every draw on this metric.
- **No suite-level superiority was established.** The transition suite's
  service-versus-sidecar claim CI was above zero, but its case-level McNemar
  p-value was 1.0, so it did not satisfy the two-part superiority rule.
- **Machinery gate: met.** The aggregate contains all three pairings from
  complete real data. The focused test suite includes and passes the synthetic
  self-versus-self check with exact McNemar p = 1 and a zero-width CI at zero.

The primary analysis is intention-to-treat over the original 531 case-runs.
No case was replaced or rerun after observing an arm's behavior.

## Local command defect and normalized service accounting

The immutable event audit binds all 15 raw draw hashes and all 177 service
session event hashes.

- Twenty local checkpoint command failures occurred in 17 sessions:
  14 unsupported or misnamed flag argparse rejections, one unsupported
  `--json-stdin` rejection, one shell-quoting rejection, and four wrapper-local
  invalid-payload rows.
- The four wrapper-local rows have HTTP status 0, null request IDs, zero
  milliseconds elapsed, and 88 result characters each. They never reached the
  API.
- All 17 affected writable sessions later committed successfully.
- The service recorded 520 actual HTTP operations, all HTTP 200: 162 `open`,
  100 `query`, 68 `read`, 15 `resume`, and 175 successful `checkpoint`
  operations. There were zero denied operations, zero 4xx, and zero 5xx.
- The 174 eligible service sessions all persisted. The other three sessions
  were the same intentionally read-only control in each draw.

does not remove any characters from the quality metric.

The replay-weighted delta is larger because removing local rows also removes

This is a harness-prompt defect, not an API failure. The measured prompt said
only `./memory checkpoint`, leaving agents to guess syntax. Behavior-selected
replacement runs would bias the service arm upward, so none were performed.
Canonical checkpoint syntax is required in the integrated harness before E04;
that follow-up is outside the measured revision.

## Conclusions

1. E01 supplies the n=3 paired machinery required by later experiment gates.
2. The current simplified service did not establish corpus-wide
   non-inferiority to writable sidecar files at the -5-claim margin. The wide CI
   still spans both material loss and modest gain, so a directional inferiority
   claim would overstate the evidence.
3. The paired cross-arm metric contradicts the proposed RuptureOps-overfetch
   mechanism: files exposed much more model-visible command output than the
   service. D01 cannot use E01 as evidence that service-versus-files overfetch
   is present.
4. Service checkpoint persistence and transition lineage were strong, but
   output completeness remained noisy and chronic claim-slot omissions
   persisted.
5. Ambiguous checkpoint command instructions caused broad local retry overhead.
   Those failures stayed in the primary result; the correct repair is canonical
   syntax in later harnesses, not selective replacement of observed E01 cases.
